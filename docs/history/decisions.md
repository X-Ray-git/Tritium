# 决策日志

## 2026-07-19：固定产品边界

背景：旧工程包含关注、点赞和较复杂的回复入口，与当前阅读客户端定位不符。

历史决策：主导航曾仅保留内容与设置；现已将内容内的推荐/热榜提升为主导航入口。继续删除远端点赞、关注、回复、收藏、私信、发现和 AI
功能，公开数量保持只读展示。回复采用单层弹层查看。

后果：新增功能必须先确认不突破只读边界，不要恢复已删除的交互入口。

## 2026-07-19：固定品牌与包名

决策：品牌色固定为 RGB(57, 97, 255) / `#3961FF`，包名改为
`io.github.xraygit.tritium`。品牌色不从图标或系统动态生成。

后果：旧包无法被新包覆盖安装；图标需要另行适配，但不能反向改变应用主题色。

## 2026-07-19：参考工程职责分离

决策：Hydrogen 只参考功能模块和知乎接口，Auto Folo 只参考设计、维护架构与发布
流程。Tritium 不复制其产品业务源码，也不修改参考工程；经确认需要完全一致的基础交互
可以复用 Auto Folo 已受控维护的上游开源实现，并在 Tritium 内独立测试和维护。目前
下拉刷新状态机属于这一例外。

## 2026-07-19：发布必须可追溯

决策：版本发布使用 `scripts/release.sh` 创建版本提交和 annotated tag；GitHub Actions
校验 tag 与 `pubspec.yaml`、执行分析和测试、注入正式签名并发布 APK。普通提交和未
签名构建不创建 GitHub Release。

## 2026-07-19：登录诊断不得泄露凭据

决策：登录检查点仅在 Debug 构建输出安全事件，隐藏查询参数和 Cookie 值；WebView
结束回调缺失时允许进度或 12 秒超时撤下遮罩。

后果：排障日志可以直接用于判断状态机，但仍不得要求用户提供 Cookie 或完整 URL。

## 2026-07-19：与 Auto Folo 共享 Android 签名

决策：Tritium 的 GitHub Actions 复用 Auto Folo 的 Android keystore，通过 Tritium
仓库独立的四项 Secrets 注入；证书和密码不进入源码仓库。

后果：两款应用的签名身份和密钥轮换相互关联，密钥泄露会同时影响两者。共享签名不
改变两个应用的包名、数据目录和更新关系。

## 2026-07-22：发布流程参考不等于版本盲从

决策：版本提交、annotated tag、签名构建和 GitHub Release 的阶段设计继续与 Auto
Folo 对齐；Flutter 与 GitHub Actions 版本需要在 Tritium CI 中独立验证。参考工程中
尚不存在的 action tag 不得直接同步。

## 2026-07-28：参考工程采用本地只读布局

决策：Hydrogen 长期放置在 `reference/hydrogen/`，作为被 Tritium 根仓库忽略的独立
Git 仓库。参考目录不使用 submodule，不进入 Tritium 的依赖、构建、测试或发布输入。

后果：维护者可以从固定路径核对实现，同时不会误提交 Hydrogen 的历史、构建产物或
签名文件。新克隆需要参考时自行放入该目录；目录缺失不得影响 Tritium 正常维护。

## 2026-07-28：阅读能力保持本地、链接能力分层兜底

决策：参考 Hydrogen 补齐 Android 外部知乎链接接收与本地阅读历史，但历史和正文
进度只写入 Tritium 本机，不同步知乎服务器。Tritium 已有原生只读页的链接内部
跳转；其他知乎内容统一转换为 HTTPS 并由系统浏览器打开。

决策：参考 Auto Folo 增加 1 像素阅读进度条，但以正文末尾而非整页最大滚动范围为
终点，避免评论懒加载让进度倒退。文章、回答和想法复用同一阅读会话组件。

后果：新增原生内容类型时必须同时补充链接解析、历史类型和标准 URL；不得借由链接
能力引入关注、点赞、评论发布等远端写操作。

## 2026-07-28 至 2026-07-29：导航玻璃和启动图标不得近似适配

决策：主导航完整复用 Auto Folo 当前移动端玻璃表面的连续圆角、渐变、方向性边缘
高光及内外阴影层次，不再用普通边框近似。Android 图标与 Auto Folo 一样只提供
静态 `mipmap`，从源图直接做无内边距圆角裁剪；不再提供会被启动器二次裁切和缩放
的 Adaptive Icon XML。

排查过程：源文件 `assets/images/logo/icon.png` 本身符合预期，但 Android 设备显示
类似“只取中央约 0.1…0.9 再撑满”的效果。这个范围只是用户帮助定位问题的近似描述，
曾被错误当成精确映射并生成固定 10% 反向补偿；该方案随后立即撤销。对比 Auto Folo
最终资源后确认，真正差异是 Tritium 的 `mipmap-anydpi-v26/ic_launcher.xml` 会让
Android 8+ 改走 108dp Adaptive Icon 图层，而 Auto Folo 只有静态 mipmap。因此最终
删除 adaptive XML、前景、背景和专用颜色资源，而不是保留任何经验缩放。

后果：以后更换 `assets/images/logo/icon.png` 后运行
`scripts/generate_logo_assets.py` 和 `dart run flutter_launcher_icons`，不得根据
单一启动器的近似显示范围增加经验缩放，也不得重新引入 adaptive 前景安全区。

## 2026-07-29：正文进度稳定性优先于变量高度惰性构建

背景：多图长正文通过 `SliverList` 按需创建语义块时，尚未出现的块与图片真实高度
会持续修正评论锚点位置。阅读进度以该锚点作为正文终点，因此分母变化会造成进度条
前后跳动；这与 Auto Folo 曾经依赖动态 `maxScrollExtent` 时的问题属于同一类。

决策：文章和回答共用的 `ChunkedHtmlSliver` 保留后台解析、语义分块和短块合并，但
改用 `SliverToBoxAdapter + Column` 一次布局所有块。图片继续使用显式比例或合理
预估占位，不通过进度动画掩盖几何变化，也不强制未知比例图片永久使用估算高度。

后果：超长正文会一次创建更多 Widget，但正文终点在开始阅读前即可确定；不得在
缺少稳定高度模型的情况下恢复变量高度 `SliverList`。

## 2026-07-29：缩略跟评保留表情语义

背景：完整楼中楼使用 `CustomHtml`，而根评论内的缩略跟评曾用正则删除全部 HTML
后直接显示纯文本，导致 `[捂脸]` 等文本表情和 `<img class="emoji">` 都无法加载。

决策：缩略跟评使用非交互的紧凑 HTML 预览，只保留文本、基础强调和知乎表情；普通
图片附件仍省略，链接不接管点击，整个预览继续用于打开只读楼中楼。

## 2026-07-29：正文进度以视口下边缘到达末尾为完成

背景：旧公式使用当前 offset 除以“正文末尾对齐视口顶端”的 offset。正文之后的评论
很短时，页面最大滚动范围可能不足以让视口顶端到达正文末尾，因此进度永远无法满格。

决策：通过 `RenderAbstractViewport.getOffsetToReveal(bodyEnd, 1)` 取得正文末尾对齐
视口下边缘的实际滚动终点，并在该终点显示 100%。正文末尾初始已经位于视口内时，
可用正文滚动距离为零，布局完成后直接显示 100%；不隐藏进度条，也不要求用户执行
没有意义的滚动。

后果：很短的正文会在打开后满格；文字虽然很短但封面、标题或作者信息让正文末尾仍
在屏幕外时，仍需滚动到末尾进入视口。恢复位置与进度保存使用同一终点，评论加载和
评论长度变化不参与计算。

## 2026-07-31：评论区改为自动加载下一页

背景：评论组件 `InlineCommentWidget` 以 `childCount: 1` 的 `SliverList` 形式内联
嵌在回答/文章/想法的正文滚动视图里。它只维护自身的分页状态（`_nextUrl`），没有
与父级滚动事件挂钩，因此在评论还有下一页时，只能渲染一个“查看更多评论”按钮，要求
用户手动点击才能继续加载。这是实现缺口而非有意的产品取舍——对照推荐流
（`RecommendPage`）已经通过监听 `extentAfter` 做了自动加载。

审查中否决过一版实现：它在评论组件内部包 `NotificationListener`，但父滚动视图是
组件的祖先，滚动通知不会向后代传播；同时它把
`RenderAbstractViewport.getOffsetToReveal(...).offset` 当作哨兵相对屏幕顶部的
坐标。该值实际是同一滚动轴上的绝对目标 offset，长文章即使已经滚到评论区也可能
一直拿数千像素的绝对值与屏幕高度比较，导致自动加载只在短内容中偶然生效。那一版
纯函数测试没有挂载真实父滚动视图，因此虽然全部通过，却没有覆盖核心链路。

最终判断：`InlineCommentWidget` 自身位于外层 `Scrollable` 的后代，可以在
`didChangeDependencies` 通过 `Scrollable.maybeOf(context, axis: Axis.vertical)`
取得祖先 `ScrollPosition`，正确注册/解除 listener。尾部仍放置 `GlobalKey` 哨兵，
但计算统一使用滚动坐标系：

`哨兵绝对 reveal offset <= 当前 pixels + viewportDimension + preloadExtent`

为何不破坏正文进度稳定性：正文进度锚点（`commentsKey`）位于评论列表**之前**，
评论加载只会让下方内容变长，不改变正文终点的滚动位置；因此自动加载评论不会触发
“阅读进度条随评论懒加载跳动”这一已记录问题。

决策：评论区尾部从固定按钮改为以自动加载为主、保留可点击兜底的三态：
- **空闲**：仍展示“查看更多评论”，兼作几何哨兵和可访问入口。
- **加载中**：转圈。
- **失败**：原来加载更多失败仅弹一次 SnackBar 就消失，改为在尾部展示“加载失败，
  点击重试”的退化态，用户可恢复。

触发逻辑抽成纯函数 `shouldAutoLoadMore`（`lib/utils/comment_auto_load.dart`），
默认 `preloadExtent = 720`，与正文评论预加载距离一致。首次页面成功和每次追加成功
后在下一帧补检，覆盖短正文或一页评论不足以填满视口的情况；真实父滚动 listener
覆盖长正文继续下滑。该阈值保持内部实现细节，不增加面向用户的技术设置。

分页请求捕获本次 `nextUrl`，通过加载锁防止并发；成功页按评论 ID 去重，并记录已经
消费的游标。追加页没有新评论、返回同一游标或回到已消费游标时立即停止，避免自动
模式不断请求和追加重复数据。加载更多错误只显示尾部重试；重新排序、首屏重载或成功
请求会清理旧错误。通用 `TritiumGlassSheet` 同时改用真实 `Material` 承载背景和
水波纹，避免排序 `ListTile` 的 ink 被装饰层遮挡。

后果：评论滑到末尾会自动拉取下一页，无需手动点击；按钮仍作为可访问和异常兜底。
评论目前仍在单个 `Column` 中保留所有已加载项，这是既有架构的内存风险；本轮不为
没有复现的性能问题扩张成 Sliver 重构，超长评论区如出现掉帧再单独设计虚拟化。
